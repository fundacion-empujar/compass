# Fork Deployment Procedure (Brújula)

How to deploy a commit (or a config change) to an **existing** fork environment.
For a first-time realm/environment bring-up, use
[`deployment-procedure.md`](deployment-procedure.md) instead.

> The fork runs two long-lived environments, **dev** and **test**, each in its
> own GCP project with its own service-account key under `iac/keys/`.
> **The dev environment serves real end-user traffic** (including live job
> fairs) — treat it like production: always deploy to **test first** as a smoke
> check, then dev.

---

## 1. Mental model — read this before running anything

There are **three** copies of "the config", and three scripts that move data
between them:

| Location | What it is |
|---|---|
| **GCP Secret Manager** (`env-vars-main`, `stack-config-main` per env) | The source of truth. |
| **`iac/cfgs/`** (`.env.<realm>.<env>`, `stack_config.<realm>.<env>.yaml`) | Manual working copy. Gitignored. **Maintained by hand** — nothing in the repo refreshes it. |
| **`iac/<module>/Pulumi.<stack>.yaml`** | Per-module Pulumi config. Gitignored. **Generated by `prepare.py`**, read by `pulumi up`. |

| Script | Reads from | Writes to | Purpose |
|---|---|---|---|
| `setup_env.py` | `iac/cfgs/` | Secret Manager | Push local config **up** to SM |
| `prepare.py` | Secret Manager | per-module `Pulumi.<stack>.yaml` | Pull SM **down**, split per module |
| `up.py` | per-module yamls + cloud APIs | GCP infrastructure | `pulumi up` per module + smoke tests |

**Critical rule — a config change is a four-step round-trip, not one push:**

```
edit iac/cfgs/  →  setup_env.py  →  prepare.py  →  up.py
```

If you run `setup_env.py` and then skip `prepare.py`, `pulumi up` reads the
**stale** per-module yamls and your change **does not deploy** — silently. The
"either run setup_env *or* prepare" shortcut is only valid for a **code-only**
deploy (see Step 2).

---

## 2. Prerequisites & the per-shell rule

- IaC virtualenv created and dependencies installed (`cd iac`, `python3 -m venv .venv`, `pip install -r requirements.txt`).
- `gcloud`, Pulumi CLI, Docker (running — the backend build builds an image).
- AWS credentials configured (Pulumi state lives in S3, so `up.py` needs an AWS profile).

```bash
cd <REPO_ROOT>/iac
export GOOGLE_APPLICATION_CREDENTIALS=<ABS_PATH_TO_ENV_SA_KEY>   # iac/keys/<env>-...json
gcloud auth activate-service-account --key-file="$GOOGLE_APPLICATION_CREDENTIALS"  # needed when switching envs
source .venv/bin/activate
```

If you forget the `GOOGLE_APPLICATION_CREDENTIALS` export, scripts fail with a
**misleading** "Reauthentication is needed — run `gcloud auth
application-default login`". The fix is almost never user reauth — it is the
missing export in *this* shell.

### Placeholder legend

| Placeholder | Meaning |
|---|---|
| `<REPO_ROOT>` | Absolute path to your local clone |
| `<REGION>` | GCP region for builds, e.g. `us-central1` |
| `<ARTIFACTS_PROJECT_ID>` | The realm-root project that stores build artifacts (shared by both envs) |
| `<ENV_PROJECT_ID>` | The GCP project of the target environment |
| `<ABS_PATH_TO_ENV_SA_KEY>` | Absolute path to the target env's SA key under `iac/keys/` |
| `<REALM_NAME>` | Pulumi realm name |
| `<ENV_NAME>` | Target environment name (e.g. the dev or test env) |
| `<BUILD_NUM>` | Build run number — increment each build |
| `<COMMIT_SHA>` | Git commit being deployed (recorded in `be-report.md` / `fe-report.md`) |
| `<AWS_PROFILE>` | Your configured AWS profile for Pulumi state |

## 3. Step 1 — Build & upload artifacts (once per commit)

Artifacts go to the shared realm-root project; both envs pull from there. Run
this **once per commit**, regardless of how many envs you'll deploy to. Pick
`<BUILD_NUM>` by incrementing the last one (see `be-report.md`/`fe-report.md`).

```bash
# (prefix with the per-shell block from Step 2)
export SENTRY_AUTH_TOKEN=$(grep -E "^SENTRY_AUTH_TOKEN=" ../backend/.env | cut -d= -f2- | tr -d '"'"'")
./scripts/build-and-upload-fe.sh <REGION> <ARTIFACTS_PROJECT_ID> ./fe-report.md <BUILD_NUM>
./scripts/upload-templates.sh   <REGION> <ARTIFACTS_PROJECT_ID>
./scripts/build-and-upload-be.sh <REGION> <ARTIFACTS_PROJECT_ID> ./be-report.md <BUILD_NUM>
```

- **Docker must be running** (backend step builds an image). The templates step
  uploads `env.template` and `stack_config.template.yaml` — make sure any new
  variables are added to `iac/templates/env.template` first.
- **`SENTRY_AUTH_TOKEN`**: the frontend build uploads sourcemaps to Sentry and
  **hard-exits if the token is set but rejected (HTTP 403)** — there is no
  skip-on-fail. Use the org-scoped CI token from `backend/.env` (sourced above),
  not a personal token from your shell profile. To skip sourcemap upload
  entirely (the bundle still ships), just don't set `SENTRY_AUTH_TOKEN`.
- `prepare.py` later fails with `NOT_FOUND` for any commit whose artifacts were
  never uploaded — **always build first**.

Backgrounding is recommended: each build takes 5–15 min.

---

## 4. Step 2 — Decide what changed

| What changed | What to run |
|---|---|
| **Code only** (no `.env` / `stack_config` change) | `prepare.py` → `up.py` |
| **`.env` or `stack_config`** (you edit `iac/cfgs/`) | `setup_env.py` → `prepare.py` → `up.py` |

> The API-Gateway request rate limit lives in code
> (`iac/backend/openapi2_template.yaml`) and ships at **build** time — it is a
> code change, not a `cfgs/` change. Cloud Run scaling, by contrast, lives in
> `cfgs/stack_config.*.yaml`.

---

## 5. Step 3 — Heads-up before `setup_env.py`: `cfgs/` can be stale

`iac/cfgs/` is a hand-maintained local file — nothing in the repo keeps it in
sync. **Optional but recommended when config changed:** if a teammate may have
updated env vars or stack config in Secret Manager since your last sync, your
local `cfgs/` is stale, and running `setup_env.py` would overwrite their change.
Before pushing config up, check Secret Manager / coordinate with whoever owns
the env so you don't clobber someone else's work. (Skip for a code-only deploy —
you won't be running `setup_env.py`.)

---

## 6. Step 4 — Edit `iac/cfgs/` (only if config changed)

Edit `iac/cfgs/stack_config.<REALM_NAME>.<ENV_NAME>.yaml` (and/or the `.env`).
**Values are strings** — quote them (`"10"`, not `10`). Cloud Run / API Gateway
keys live under `backend.config` (e.g. `cloudrun:max_instance_count`,
`cloudrun:max_instance_request_concurrency`, `cloudrun:min_instance_count`,
`cloudrun:cpu_limit`, `cloudrun:memory_limit`, `cloudrun:request_timeout`,
`api_gateway:timeout`). Keep `api_gateway:timeout` **≥** `cloudrun:request_timeout`
or smoke tests time out. See `iac/templates/stack_config.template.yaml` for the
full shape.

---

## 7. Step 5 — `setup_env.py` (only if you edited `cfgs/`)

```bash
# (prefix with the per-shell block from Step 2, using the target env's SA key)
./scripts/setup_env.py --secrets-expire-time=never \
  --realm-name=<REALM_NAME> --env-name=<ENV_NAME> --config-files-dir=./cfgs
```

This uploads **both** `cfgs/.env.*` **and** `cfgs/stack_config.*.yaml` to Secret
Manager — even if you changed only one, both go up, so make sure the unchanged
one is also current (see the Step 3 heads-up).

---

## 8. Step 6 — `prepare.py`

```bash
# (prefix with the per-shell block from Step 2, using the target env's SA key)
./scripts/prepare.py --realm-name <REALM_NAME> --env-name <ENV_NAME> \
  --target-git-sha <COMMIT_SHA> --target-git-branch forkout/main
```

Confirm `iac/backend/Pulumi.<stack>.yaml` shows the values you expect **before**
continuing. (Never run `setup_env.py` afterwards from this state — `prepare.py`
writes a metadata block that would leak into Secret Manager if re-uploaded.)

---

## 9. Step 7 — `up.py`

```bash
# (prefix with the per-shell block from Step 2, using the target env's SA key)
export AWS_PROFILE=<AWS_PROFILE>
./scripts/up.py --realm-name <REALM_NAME> --env-name <ENV_NAME>
```

`AWS_PROFILE` is required (Pulumi state lives in S3). Run in the background —
5–15 min. It deploys six modules **sequentially**: `environment → dns → auth →
frontend → backend → common`, running smoke tests against each module's
`/version` endpoint before moving on.

---

## 10. Step 8 — Verify

```bash
# Cloud Run scaling
gcloud run services describe cloudrun-service \
  --project=<ENV_PROJECT_ID> --region=<REGION> \
  --format="value(spec.template.metadata.annotations,spec.template.spec.containerConcurrency)"

# API Gateway quota
SVC=$(gcloud endpoints services list --project=<ENV_PROJECT_ID> --format="value(NAME)" | head -1)
LATEST=$(gcloud endpoints configs list --service="$SVC" --project=<ENV_PROJECT_ID> \
  --limit=1 --format="value(CONFIG_ID)")
gcloud endpoints configs describe "$LATEST" --service="$SVC" \
  --project=<ENV_PROJECT_ID> | grep -A 7 "^quota:"
```

---

## 11. Standard multi-env deploy order

1. Build phase — **once** (Step 1).
2. If config changed: edit **both** envs' `cfgs/` files (Step 4).
3. **test**: `setup_env.py` (if cfgs changed — mind the Step 3 heads-up) → `prepare.py` → `up.py` → verify.
4. **dev**: same sequence. Only proceed once test is green.

---

## 12. Common pitfalls

| Symptom | Cause / fix |
|---|---|
| `prepare.py` → `NOT_FOUND` | Artifacts not uploaded for that commit. Run the build phase first. |
| `pulumi up` deploys old values after a `cfgs/` edit | Forgot `prepare.py` between `setup_env.py` and `up.py`. The per-module yamls were never regenerated. |
| Smoke tests time out | `api_gateway:timeout` < `cloudrun:request_timeout`. Keep them equal. |
| "Reauthentication is needed / `gcloud auth application-default login`" | You didn't `export GOOGLE_APPLICATION_CREDENTIALS` in *this* shell. Re-run the per-shell block. |
| Frontend build hard-exits during sourcemap upload | `SENTRY_AUTH_TOKEN` set but rejected (403). Use the org CI token from `backend/.env`, or don't set the token. |
| Your config change "didn't take" | The `setup_env.py`-or-`prepare.py` shortcut only holds for code-only deploys. A `cfgs/` change needs **both**, in order. |

Out-of-band quotas not managed in this repo: the Gemini API (pay-as-you-go on
the project) and the MongoDB Atlas connection ceiling (managed in the Atlas UI).
